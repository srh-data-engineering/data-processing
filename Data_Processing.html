2 Batch Processing

Batch processing collects and processes large volumes of historic data at scheduled intervals. Jobs run offline, results are not immediately visible, but re-execution is always possible — making it suitable for complex transformations over terabytes of stable data.

Key trait: Runtime ranges from minutes to hours or even days. The dataset is bounded — you know its size upfront.

3 Stream Processing

Stream processing handles live, unbounded event streams in real-time or near-real-time. Unlike batch, the dataset is never fully available — events arrive continuously and must be processed as they come. Re-execution of past events is generally "impossible" without a replay mechanism like Kafka offsets.

Key trait: Runtime is real-time or near-real-time (milliseconds to seconds). The dataset is unbounded — you never know when it ends.

Example Stream Data Flow

1. Collect

Kafka Topic or Flume ingests events from producers (sensors, apps, users)

2. Process

Spark Streaming or Flink applies transformations, aggregations, windowing

3. Store

Results land in MapR-DB, HBase, or Cassandra for low-latency access

4. Analyze

Spark SQL, Apache Drill, or JSON APIs serve queries over live results

Message Broker / Queue Pattern

RoleDescriptionExamples
ProducerPublishes events to named queues/topicsIoT sensors, web apps, microservices
BrokerBuffers and routes messages; decouples producers from consumersApache Kafka, RabbitMQ
ConsumerSubscribes to queues and processes eventsApache Spark, Flink, Flume
Kafka's strength: Topics are append-only, durable logs. Consumers track their own offset, enabling replay and multiple independent consumers reading the same stream.

4 Spark vs Flink

Spark and Flink are the two dominant distributed processing frameworks. They take fundamentally different approaches: Spark is a batch engine that emulates streaming via micro-batches; Flink is a streaming engine that treats batch as a bounded stream.

DimensionApache SparkApache Flink
Primary modelBatch framework emulating streamsStream framework emulating batch
Stream processingMicro-batches (cuts stream into small time windows)Processes each event individually as it arrives
Batch processingNative, highly optimizedBounded stream (batch = finite stream)
LatencySeveral secondsMilliseconds to seconds
MaturityHigh — large ecosystem, massive communityMedium — growing ecosystem & community
Use whenReliability > latencyLatency > reliability
Choose Spark when: You need a proven, well-supported platform; you have complex ML pipelines; you can tolerate a few seconds of latency; or your team has existing Spark expertise.
Choose Flink when: You need true event-time processing with sub-second latency; you are building fraud detection, real-time recommendations, or financial tick processing.

5 Lambda Architecture

Lambda Architecture solves the tension between batch accuracy and streaming speed by running both pipelines in parallel and merging their outputs in a serving layer. A single streaming source (e.g. Kafka) fans out to two layers simultaneously.

Lambda Architecture — Layer View

(e.g. Kafka)

Batch Layer

  • e.g. Hadoop HDFS
  • → Batch Processing (MapReduce)
  • → Batch Views (Hive)

Stream (Speed) Layer

  • Low-latency processing
  • e.g. Spark, Flink, Storm

  • Merges Batch + Real-Time Views
  • Low-latency query responses

👤 Data Scientist
🌐 Web App

Trade-off: Lambda is powerful but complex — you maintain two separate codebases (batch + stream) for the same logic. The Kappa Architecture simplifies this by using only a streaming layer, treating historical reprocessing as a large replay.

Batch Layer Characteristics

Immutable, append-only data sink. High latency (hours to days). Provides accurate, complete historical views. Fault-tolerant and replayable.

Speed Layer Characteristics

Low-latency, approximate views. Compensates for batch layer's high latency. Only covers recent data not yet in batch views. Discarded once batch catches up.

7 The ETL Process

ETL (Extract, Transform, Load) is the foundational pattern for data warehousing. Data is extracted from heterogeneous source systems, transformed on a dedicated staging server outside the data warehouse, and only clean, structured data is loaded into the target.

Key invariant: In ETL, the data warehouse contains only transformed data. Raw data never enters the warehouse — transformation happens externally on a staging server.

1. Extract

Pull data from source systems: relational databases (SQL queries), flat files (CSV, JSON, XML), REST/SOAP APIs, web scraping, streaming sources.

2. Transform (Staging)

Apply business rules, schema normalization, cleaning, deduplication, enrichment — all on an external staging server, not inside the DW.

3. Load

Write only transformed, validated data into the target: Hadoop HDFS, Hive, Relational DB, Data Warehouse, Data Mart, or reporting systems.

Common Transformation Operations

OperationDescriptionExample
FilteringRemove unwanted rowsKeep only bookings from 2024
MappingRename or cast field typescountry_code → country_name
AggregationGROUP BY, COUNT, SUM, AVGDaily booking totals by country
JoiningCombine tables on a keybookings JOIN countries_code
DeduplicationRemove duplicate recordsDISTINCT on user_id + date
ValidationCheck constraints, handle nullsReject rows with null email
EnrichmentAdd computed fieldsDerive age bucket from DOB

Transform Example — Bookings Aggregation

Source tables: bookings (id, email, country_code, platform, user_id, listing_id, created_at) + countries_code (country_code, country_name)

Target table: bookings_daily (date_d, country_name, platform, total)

-- SQL transformation on staging server
SELECT
    DATE(b.created_at)   AS date_d,
    c.country_name,
    b.platform,
    COUNT(*)             AS total
FROM bookings b
JOIN countries_code c ON b.country_code = c.country_code
GROUP BY DATE(b.created_at), c.country_name, b.platform;

8 ELT Process & ETL vs ELT

ELT (Extract, Load, Transform) flips the classic order: raw data is loaded directly into the data warehouse first, then transformed in-place using SQL. This approach is enabled by the compute power of modern cloud data warehouses (Snowflake, BigQuery, Redshift).

Key invariant: In ELT, the data warehouse contains both raw and transformed data. No staging server required — transformation happens inside the warehouse via SQL.

9 ETL Tools

The ETL tooling landscape spans from enterprise GUI-based products to open-source Python libraries. Choice depends on team skill, integration requirements, budget, and whether you need GUI observability or programmatic control.

Commercial / Paid

StitchData, Talend — plug-and-play GUI, 100s of pre-built connectors (SaaS, NoSQL, SQL), monitoring dashboards, configurable load schedules.

Analytics Platform ETL

Google Data Studio, Tableau — basic data loading bundled with BI tools; limited integration catalog; sufficient for reporting-only use cases.

Open-Source Python

Pandas, PETL, PySpark — programmatic control, free, flexible; require setup and integration work. Best for engineering teams.

Apache NiFi (EtL)

NiFi — GUI-based dataflow routing tool. More "EtL" (small t) — moves and lightly transforms data between systems. Not a full ETL engine.

PySpark ETL — Bookings Aggregation

from pyspark.sql import SparkSession
from pyspark.sql.functions import col, count, to_date

spark = SparkSession.builder \
    .appName("ETL_Pipeline") \
    .getOrCreate()

# Extract
bookings = spark.read.format("csv") \
    .option("header", "true") \
    .load("hdfs:///raw/bookings/")

countries = spark.read.format("parquet") \
    .load("hdfs:///ref/countries_code/")

# Transform
result = bookings \
    .join(countries, "country_code") \
    .groupBy(to_date("created_at").alias("date_d"),
             col("country_name"), col("platform")) \
    .agg(count("*").alias("total"))

# Load
result.write.format("parquet") \
    .mode("overwrite") \
    .save("hdfs:///warehouse/bookings_daily/")

Pandas ETL — Same Transformation

import pandas as pd

# Extract
bookings  = pd.read_csv("bookings.csv")
countries = pd.read_csv("countries_code.csv")

# Transform
merged = bookings.merge(countries, on="country_code")
merged["date_d"] = pd.to_datetime(merged["created_at"]).dt.date

result = merged.groupby(["date_d", "country_name", "platform"]) \
    .size().reset_index(name="total")

Spark Streaming — Word Count (Scala)

val spark = SparkSession
  .builder()
  .master("local")
  .appName("Socket_Streaming")
  .getOrCreate()

// Initialize Socket Stream — input could also be Kafka, Flume, Kinesis
val socketStreamDf = spark.readStream
  .format("socket")
  .option("host", "localhost")
  .option("port", 4711)
  .load()

val words      = socketStreamDf.as[String].flatMap(_.split(" "))
val wordCounts = words.groupBy("value").count()

val query = wordCounts.writeStream
  .outputMode("complete")
  .format("console")   // Output could also be HDFS, Kafka, Kinesis
  .start()

query.awaitTermination()

10 Key Concepts

Batch Processing

Processing large volumes of bounded, historic data at scheduled intervals. Runtime: minutes to days. Re-execution possible.

Stream Processing

Processing unbounded live event streams in real-time or near-real-time. Runtime: milliseconds to seconds. Re-execution generally "impossible".

ETL

Extract, Transform, Load. Transformation happens on an external staging server; only clean data enters the data warehouse.

ELT

Extract, Load, Transform. Raw data loaded into the DW first; transformation performed inside the DW using SQL. Enabled by modern cloud DWs.

Data Lake

Schema-on-read storage for raw data at any scale. Typically Hadoop HDFS or cloud object storage (S3). Stores structured, semi-structured, and unstructured data.

Data Warehouse

Schema-on-write store optimized for analytical (OLAP) queries. Contains cleaned, structured data. Examples: Snowflake, BigQuery, Redshift, Hive.

Data Mart

Subject-specific subset of a data warehouse. Serves a single business domain (e.g. finance, marketing). Example: PostgreSQL-based sales mart.

Lambda Architecture

Dual-pipeline pattern combining a Batch Layer (accurate, slow) and Speed Layer (approximate, fast), merged in a Serving Layer.

Micro-Batch

Spark's approach to streaming: the stream is sliced into small time windows (e.g. 1 second) and each window is processed as a mini-batch job.

Message Broker

Middleware that decouples event producers from consumers via named queues/topics. Buffers events for reliability. Example: Apache Kafka.

Tumbling Window

Fixed-length, non-overlapping time window. Each event belongs to exactly one window. Used for per-period aggregations (e.g. hourly counts).

Hopping Window

Fixed-length, overlapping window that advances in fixed steps. An event can belong to multiple windows (window size > hop size).

Sliding Window

Event-driven window that slides forward on every incoming event. Each window contains at least one event and overlaps with its neighbors.

Session Window

Arbitrary-length window bounded by a gap timeout or explicit start/end events. Useful for modeling user sessions (login → logout).

Staging Server

In ETL, the intermediate server where data is extracted and transformed before loading into the DW. Keeps raw/sensitive data out of the warehouse.

Apache Kafka

Distributed append-only event log. Topics are retained durably; consumers track their own offset enabling replay and multiple independent consumers.

11 Glossary

Apache Flink
Native stream processing engine. Processes each event as it arrives; treats batch as bounded stream. Millisecond latency.
Apache Kafka
Distributed event streaming platform. Durable, append-only topic logs. Consumers track offsets independently, enabling replay.
Apache Spark
Unified analytics engine. Batch-first; emulates streaming via micro-batches. In-memory DAG execution. Rich ML, SQL, and streaming APIs.
Apache Storm
Low-latency distributed stream processing topology. Precursor to Flink and Spark Streaming for real-time computation.
Batch Layer
In Lambda Architecture: immutable master data sink that feeds batch processing jobs producing batch views. High latency, high accuracy.
Cassandra
Wide-column distributed NoSQL store. High write throughput, tunable consistency, no single point of failure. Used for real-time view storage.
Data Acquisition
Stage where data is ingested from sources into the system. Tools: Sqoop (RDBMS→HDFS), Kafka (streaming), Flume (log streaming).
Data Lake
Schema-on-read storage for raw data at any format and scale. Central repository for structured, semi-structured, and unstructured data.
Data Mart
Subject-specific subset of a data warehouse tailored for a business domain (finance, sales, HR). Smaller scope, faster queries.
Data Warehouse
Schema-on-write analytical store optimized for OLAP queries. Contains clean, structured, historical data. Examples: Snowflake, Redshift, Hive.
ELT
Extract, Load, Transform. Raw data loaded directly into DW; transformation occurs in-place via SQL. No staging server required.
ETL
Extract, Transform, Load. Data is cleaned on a staging server before entering the DW. Classic data warehousing pattern.
Event Time
The timestamp when an event actually occurred (vs. processing time — when it was received). Critical for correct windowed aggregations with late-arriving data.
Hadoop HDFS
Hadoop Distributed File System. Block-replicated (3×), rack-aware, designed for sequential reads of large files. Foundation of the Hadoop ecosystem.
HBase
Wide-column store on top of HDFS. Provides random read/write access to individual cells. Used when HDFS sequential reads are too slow.
Lambda Architecture
Pattern combining Batch Layer + Speed Layer → Serving Layer. Provides complete, accurate historical views and low-latency recent views simultaneously.
Latency
Time between an event occurring and its processed result being available. Batch: minutes–days. Stream: milliseconds–seconds.
MapReduce
Hadoop's parallel computation model. Map phase applies functions per record; Reduce phase aggregates. Writes intermediate results to disk between stages.
Message Broker
Middleware that decouples producers from consumers. Buffers events in queues/topics. Enables fan-out (one topic → many consumers).
Micro-Batch
Spark Streaming's approach: slice the stream into small time intervals and process each as a mini-batch. Latency = batch interval (typically 0.5–10s).
NiFi
Apache NiFi. GUI-based dataflow tool for routing and moving data between systems with light transformations. "EtL" (small t) rather than full ETL.
OLAP
Online Analytical Processing. Query pattern focused on aggregations over large historical datasets. DWs are optimized for OLAP workloads.
Pandas
Python DataFrame library for in-memory data manipulation. Loads full dataset into RAM. Best for single-machine ETL and data science workflows.
PETL
Python ETL library. Table-based, iterator-driven (lazy evaluation). Streams data row-by-row for constant memory use. Good for large file ETL on a single machine.
Producer–Consumer
Messaging pattern where producers publish events to a broker and consumers subscribe. Decouples systems and enables async processing at scale.
PySpark
Python API for Apache Spark. DataFrame and SQL abstractions for distributed ETL and ML. Scales from a laptop to a 1000-node cluster.
Redis
In-memory key-value store. Sub-millisecond reads/writes. Used for caching aggregated results and session data in streaming pipelines.
Serving Layer
In Lambda Architecture: the layer that merges batch views and real-time views, exposing a unified query API to applications and analysts.
Sliding Window
Stream processing window triggered by each event. Fixed duration, overlapping. Every window contains at least one event; slides continuously forward.
Sqoop
Apache Sqoop. Bulk data transfer tool between RDBMS and Hadoop HDFS. Used in Data Acquisition stage for importing relational tables into the lake.
Speed (Stream) Layer
In Lambda Architecture: low-latency layer that processes incoming events in real-time, compensating for the batch layer's high latency on recent data.
Tumbling Window
Fixed-length, non-overlapping stream window. Each event belongs to exactly one window. Used for per-period aggregations (e.g. counts per 4 seconds).
